# AI-журнал (Лабораторные работы 6-8)

## Лабораторная работа №6 (Разработка функционала)
1. **Дата/этап**: Реализация сервисного слоя CRUD операций.
2. **Задача**: Получить структуру CRUD-класса для Заявок на Python (FastAPI/SQLAlchemy).
3. **Модель**: Gemini 1.5 Pro.
4. **Промпт 1 (Неудачный)**: "Напиши CRUD для заявок на питоне."
5. **Анализ неудачного ответа**: Модель написала код на чистом sqlite3 с хардкодом SQL, без использования Pydantic-схем, без асинхронности и без разделения на слои. Это не подходит под современные стандарты FastAPI.
6. **Промпт 2 (Улучшенный)**: "Выступи Senior Python Developer. Напиши CRUD-класс для сущности Request (Заявка) с использованием SQLAlchemy 2.0 (асинхронно) и Pydantic-схем. Реализуй методы: create, get_by_id, get_all (с фильтром по status_id), update_status и delete. Приложи обработку ошибок, если запись не найдена."
7. **Контекст**: Передана структура БД из ЛР №5.
8. **Результат**: Сгенерирован класс `RequestCRUD` с методами `get`, `create`, `update` на базе SQLAlchemy `AsyncSession`.
9. **Проверка**: Код проверен линтером (mypy) и запущен локально.
10. **Доработка**: Убрал лишние импорты, добавил кастомный эксепшн `HTTPException(404)` прямо в сервисе, если заявка не найдена при удалении.
11. **Почему такая модель/промпт**: Нужно было получить production-ready код с типизацией.
12. **Итог**: Код лёг в основу файла `src/crud.py`, сэкономлено время на написание рутинных SQL-алхимия запросов.

## Лабораторная работа №7 (REST API)
1. **Дата/этап**: Проектирование контракта API.
2. **Задача**: Спроектировать эндпоинты, HTTP-коды и Pydantic-схемы для Заявок.
3. **Модель**: Gemini 1.5 Pro.
4. **Промпт**: "Спроектируй REST API контракт для сущности Request (Система заявок). Опиши эндпоинты, методы, HTTP-статусы ответов (успех и ошибки) и JSON-схемы (Pydantic) для POST и PATCH запросов."
5. **Контекст**: ТЗ из ЛР №1, требования к минимальному набору эндпоинтов из методички.
6. **Результат**: Предложена таблица эндпоинтов и код Pydantic схем (`RequestCreate`, `RequestUpdate`, `RequestResponse`).
7. **Проверка**: Сверка с методичкой. Модель забыла эндпоинты для Справочников (Категории, Статусы).
8. **Доработка**: Добавлены эндпоинты `GET /categories` и `GET /statuses` вручную. В схемы добавлено поле `created_at` с `datetime.utcnow`.
9. **Почему такая модель/промпт**: Модель хорошо проектирует API и генерирует валидные Pydantic-модели.
10. **Итог**: Контракт реализован в `src/main.py` и `src/schemas.py`, протестирован через Swagger UI (/docs).

## Лабораторная работа №8 (Деплой и Docker)
1. **Дата/этап**: Упаковка приложения в Docker.
2. **Задача**: Написать production-ready Dockerfile для FastAPI.
3. **Модель**: Gemini 1.5 Pro.
4. **Промпт**: "Напиши Dockerfile для FastAPI приложения на Python 3.12. Используй uvicorn. Приложение лежит в папке src/. Добавь health-check. Учти безопасность (запуск не от root) и кеширование слоев requirements.txt."
5. **Контекст**: Структура проекта (requirements.txt в корне, код в src/).
6. **Результат**: Сгенерирован многослойный Dockerfile с созданием пользователя `appuser` и инструкцией `HEALTHCHECK`.
7. **Проверка**: Сборка образа `docker build -t req-sys .` прошла успешно, контейнер стартует.
8. **Доработка**: Убрал `HEALTHCHECK` из самого Dockerfile и перенес его в `docker-compose.yml`, так как это более гибкий подход для локальной разработки. Добавил `.dockerignore`.
9. **Почему такая модель/промпт**: Модель знает лучшие практики написания Dockerfile (кеширование слоев, non-root user).
10. **Итог**: Файлы `Dockerfile` и `docker-compose.yml` добавлены в корень репозитория. Приложение запускается одной командой.
